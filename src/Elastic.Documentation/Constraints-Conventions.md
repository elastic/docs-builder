# Constraints conventions: what a loader hides, and how the model shows it

A loader may trim, default, coerce, drop or collapse what a file wrote. The build keeps using the result; the model additionally records what was hidden, so a rule can say "the file wrote X". The loader's behaviour never changes. All of this is AOT-safe: the loader already walks the nodes, no reflection.

| The loader... | The model keeps | Rule reads |
| --- | --- | --- |
| drops keys it does not read | `IReadOnlyList<string> UnknownKeys` on the record built from that mapping, in the order written. Filled with `UnknownYamlKeys.Of(written, known...)` (Configuration/Converters). `[IgnoreEquality]`. | `Each` over the keys, one violation per key, Warning |
| coerces text into a bool or an enum (invalid text falls back to a value) | `<Member>Raw` (`string?`), the text as written; null when the model was not loaded from a file. `[IgnoreEquality]`. | the raw text parses, e.g. `Enum.GetNames<T>().Contains(raw, OrdinalIgnoreCase)` |
| defaults, trims or normalises a value | `Nullean.Entities.Authored<T>` when the member may change type; otherwise the same `<Member>Raw`. | `Raw` against the form the build expects |
| chooses between files | `SourceFileName` (`string?`) on the model | the name |
| collapses duplicate keys of a dictionary | a `DuplicateKeys` list, filled where the dictionary is built (none needed yet) | `Unique` |
| throws on bad input | nothing: the load fails with the loader's message, there is no model. The row stays with the loader. | none |

Rules for the pieces:

- A raw/unknown field never takes part in equality (`[IgnoreEquality]`) and has a default, so code that builds the model by hand needs no change and a hand-built model breaks no rule (null raw is "not authored").
- A rule about something the loader already reports (a diagnostic, an exception) is not added: one report only. Log the row as a gap instead.
- A default that is the dominant idiom of the shipped files (`apm-server:` with no settings, `versioning` omitted because it equals the product id) is not a violation; the field is not added.
- Severity of a new rule on a silent coercion is Warning, unless the catalogue says otherwise.

## Loader pipeline: Parse + Map + Rules

Every loader is three things and nothing else, run through `LoaderPipeline` (Elastic.Documentation.Configuration/Loading):

```csharp
public static Result<SearchTuning> Load(ConfigurationFileProvider provider) =>
    LoaderPipeline.Run(
        "search.yml",
        parse: ReadDto,                       // the only code that touches the DTO (internal)
        map: ToRecord,                        // DTO -> anemic record; findings of its own go in `extra`
        rules: SearchTuningConstraints.All);  // the aggregate's set, from Elastic.Documentation
```

- `Run` catches a step that throws and returns it as an error diagnostic carrying the exception's message, runs `rules.Report` exactly once, and returns `Result<T>` (an error means no value; `errorsAreFatal: false` returns the value with its errors for a caller that reports and continues, a docset or a navigation). `Check` is the same last step for a record built elsewhere; `Build` only builds, for a part whose rules relate it to another part (a pair set the loader runs once both exist).
- The raw parse helpers (`CreateProducts`, `CreateSearchConfiguration`, `AssemblyLoader.Deserialize`, `SiteNavigationLoader.Deserialize`, `CodexSiteLoader.Deserialize`, `ChangelogConfigurationLoader.DeserializeConfiguration`, ...) are `internal`. Outside Configuration there is no way to get a record from text except through the checked loader. Tests see them through `InternalsVisibleTo`.
- A docset has one entry, `DocumentationSetLoader.Load(...)`, which parses, maps and resolves against the catalog (the pair set `DocumentationSetInCatalog`) and returns `Result<LoadedDocumentationSet>`. `LoadMetadata` is the one deliberate unchecked entry (codex reads the registry of repositories it does not build); it returns a `Result` too and is pinned by a test.
- `LoaderEntryPointTests.NoPublicLoaderMethodReturnsAnUncheckedDomainRecord` fails when a public method of a `*Loader` type returns a domain record instead of `Result<T>`, unless it reports to a collector it is given.

## Loader recipe: build, check once, hand the result on

A loader is the one place that checks the entity it builds; nothing downstream checks it again.

1. Build the entity. When a rule relates two things, the loader builds the pair record itself, e.g. `new DocumentationSetInCatalog(docset, products)`.
2. `var report = Set.All.Report(entity);` runs every rule once and reports all of them, not the first.
3. Hand the report on: `Result.From(report, file)` (carries every diagnostic; `HasErrors` is true when a rule of Error severity was broken) or, where the loader owns a collector, `collector.Write(report, file)`, which returns whether the entity is usable. Both go through `ConstraintReport<T>.ToDiagnostics`, the only violation-to-diagnostic mapping, so every diagnostic carries the rule's id as `Diagnostic.RuleId`. Match on that, never on message text.
4. Drop items only through the report, by the typed rule handle: `report.Keep(items, Set.SomeRule)` or `report.Rejected(Set.SomeRule)`, never by comparing a `ConstraintId` string. Only an Error rejects an item; a Warning never drops one.
5. Never check in a callee. A caller of a loader uses `result.EmitTo(collector)` and `result.HasErrors`; it does not run the set again. The `Check(...)` one-liners on the sets are gone: use `Set.All.Report(...)`.
6. Startup-critical configuration stops the process in one place, the composition root: `Loader.Load(...).OrThrow()` throws a `ConfigurationException` whose message lists every error and which carries every diagnostic.

## Ownership: three owners, by lifetime

Services never load. Whoever owns a loader is decided by how long what it loads lives.

1. **Global configuration (the process).** `GlobalConfigurationLoader.LoadOnce(provider)` is the only entry: `assembler.yml`, `versions.yml`, `products.yml`, `legacy-url-mappings.yml` and `search.yml` load once per provider and come back as one `Result<GlobalConfiguration>` carrying every diagnostic, so `OrThrow()` at the composition root (`AddDocumentationServiceDefaults`) lists every error of every file. Its non-error diagnostics are registered as the singleton `StartupDiagnostics`. The owner of a collector drains it exactly once per process: `DocumentationTooling` does it when it creates the console collector, so every command family (build, codex, changelog, assembler...) reports a catalogue warning once. A host with no collector (API, MCP server) calls `StartupDiagnostics.LogTo(logger)`; a lambda that loads one file itself (`AssemblyLoader.LoadYaml`) decides for itself and ignores warnings. `related-learning.yml` is not global: it loads on first use (`IConfigurationContext.RelatedLearning`), because only documentation builds need it.
2. **Context-scoped (a build, an assemble run, a codex).** The context owns its loader and loads once (docset: `BuildContext`; navigation: `AssembleContext`), and the context is created once per run, never per service. `AssembleContextProvider` (a DI singleton) hands every assembler service and command the same `AssembleContext` for an environment/collector/directory combination, so the navigation is parsed, checked and its diagnostics emitted once per run; a service asks `contexts.Get(environment, collector, fileSystem)` instead of `new AssembleContext(...)` (tests may still construct one directly). A docset is per repository by nature: one `BuildContext` per docset is the intended lifetime. What a directive needs from the run comes from the build context, not from a loader of its own: `BuildContext.PrivateRepositoryNames` (the assembly configuration loaded at startup) and `BuildContext.BundleLoader` replace `AssemblyLoader.LoadOnce` and `new BundleLoader` inside `{changelog}`. A directive's own YAML/JSON body with no domain record and no constraint set (`{settings}` tables, `{whatsnew}` central config, the Storybook registry, csv includes) is a directive-local format: it stays with the directive.
3. **Artifact loaders (a command or a call).** Changelog configuration, entries, bundles, link manifests, the sync plan. `ChangelogConfigurationLoader` returns `Result<ChangelogConfiguration>` (`Load`, `LoadRequired`, `LoadForProfileMode`); the command owns one and hands it to the services it creates (`configurationLoader:`), a service created without one (tests, CI commands over a runner temp file system) makes its own. It is deliberately not cached: a command reads `changelog.yml` once or twice, and a cache keyed by path would serve a stale file to anything that rewrites it (every test does).

**Plain transport, on purpose.** Three reads stay in their service because there is no domain record with a constraint set to check them against, so a loader would only rename `JsonSerializer.Deserialize`: the redirects mapping `DeployUpdateRedirectsService` pushes to the key-value store (`Dictionary<string, string>`; a missing or unparsable file is already an error diagnostic on the file), the build's `GenerationState` (`DocumentationGenerator.GetPreviousGenerationState`, a private cache of the previous build that is only a hint for incremental builds), and the Storybook registry (a directive-local format, see above). The moment one of them gains a constraint set it moves into a loader next to the others. The link-index snapshot `CodexCloneService` reads is not one of them: it goes through `LinkLoader.LoadRegistry`.

`LoaderEntryPointTests.NoPublicLoaderMethodReturnsAnUncheckedDomainRecord` has no exemption left: a public loader method returns `Result<T>`, even where the parser reports to a collector internally (the changelog loader buffers that into the result).

A rule is not wired into a loader when something already reports the same problem with a different message or severity, or when the rule is stage dependent (its description says so): wiring it would report twice or report at the wrong stage. Log the row as a gap instead.

## Artifact loaders: release notes

Changelog entries and bundles are artifacts read from many places (a folder, CDN content, S3, git), so their loader is not one `Load` but a small set of entry points in `Elastic.Documentation.Configuration/ReleaseNotes`, and **nothing else touches the file's shape**: the DTOs (`ChangelogEntryDto`, `ProductInfoDto`, `Bundle*Dto`, `*MinimalDto`) and `ReleaseNotesSerialization` are `internal` (tests see them through `InternalsVisibleTo`).

- `ReleaseNotesLoader.LoadEntry(text, fileName, file?)` and `LoadBundle(text, file)` parse, map and check once, returning `Result<T>`. A file that does not parse (or is empty) is an error diagnostic and no record; a file that parses always returns its record with every finding, so the caller, which knows whether a rule error stops it, decides. `Serialize(entry|bundle)`, `NormalizeYaml` and `ToEntry(BundledEntry)` are the writer side: a writer never needs a DTO.
- `BundleLoader.LoadBundles(folder)` and `LoadBundlesFromContent(...)` (CDN) return `Result<IReadOnlyList<LoadedBundle>>`. The findings are always in the result (no optional callback): an unparseable bundle or an entry without inline content is an error diagnostic (the bundle or entry is skipped), a broken rule is reported at its own severity, then `LoadedBundleConstraints` runs once on what was loaded. The directive forwards each diagnostic; the CDN fetcher forwards each as a warning (an inferred product must not fail the build).
- **Stage-dependent rules are separate sets, not flags.** A rule whose description says "stage dependent" does not run at read time. The read-stage sets are `ChangelogEntryReadConstraints.All` (marker integrity only), `BundleReadConstraints.All` (not `bundle-entries-inlined`, which the loader enforces with its own pinned warning, nor `bundle-entry-files-unique`, a render CLI rule) and `LoadedBundleReadConstraints.FromContent` (no file-name convention for CDN objects). Each is written as `Full.All.Without(Full.RuleA, Full.RuleB)` with typed handles (`ConstraintSet<T>.Without(params Constraint<T>[])`), so the suppression is visible, survives a rename, and a rule removed from the full set breaks the build.
- The authoring stage reads the file's own shape, which a record cannot carry (an unrecognized type, `versions` on an entry, the raw lifecycle text), so `ChangelogEntryValidator` (`validate-entries`) lives beside the loader and takes the file's text, not a DTO. Its messages are pinned by tests and differ from the constraint set's, so it stays the validate stage's own report; `BundleBuilder` likewise keeps its `missing required field` messages.
- `LoaderEntryPointTests.ReleaseNotesDtosAreInternal_AndTheirLoadersReturnCheckedResults` fails when a release-notes DTO or the raw serializer is public, or when `ReleaseNotesLoader`/`BundleLoader` hand out a record (or a collection of records) outside a `Result<T>`.

## Domain operations: derive, then re-check

A record that is not read from a file (built from a pull request, assembled from files, scrubbed, merged, amended) is made by a **domain operation**, never by `new` or `with` in a service. The release-notes records have them in `Elastic.Documentation/ReleaseNotes` (`ChangelogEntry.FromPullRequest/Create/Marker/SourcePointer/CanonicalKeyAndMarkers`, `ProductReference.Parse`, `Bundle.Assemble/ForRelease/Finalize/AmendOf/ApplyAmends/WithoutPrivateLinks`, `BundledEntry.Inline/Exclusion/AppendContinuation/ToNote`, `entry.ToBundledEntry(file, checksum)`, `LoadedBundle.MergeByTarget`, `LinkAllowlist`).

- **Pure.** No IO, no clock (the caller passes `today`), no collector. A finding is a diagnostic in the result, in the order it was found, so a service forwards them with the same messages as before (`result.EmitTo(collector)`).
- **Returns `Result<T>`** (`Elastic.Documentation.Diagnostics`), the record checked by the aggregate's set. The set is the stage's: the read-stage sets (`ChangelogEntryReadConstraints`, `BundleReadConstraints`, `LoadedBundleReadConstraints`) unless the rule the operation must hold is stage dependent, in which case the set is written `Full.All.Without(handles)` like they are; a pinned message is never weakened to make an operation pass.
- **Built, then derived.** `DomainOperation.Built` is for a record made from facts that were never in a file: the result carries every finding of the set. `Derived` is for a record made from one that was already checked: the set runs again (a derivation can break a rule its source kept, so the result is re-checked), but only the errors are in the result, because the warnings the source carried were reported when it was read. A caller of `Derived` writes `result.EmitErrorsTo(collector)`.
- **The value rides along.** `Result.From` keeps the value even when a rule of Error severity is broken, so a caller that tolerates the finding can still use it; `EmitErrorsTo` returns null instead.
- **A part with no set of its own** (`ProductReference`, `BundledEntry`) is not wrapped in a `Result` that checks nothing: its operations return the part, and the entry or bundle that holds it is what is checked.
- **Where two copies differed, the difference is a parameter**, not a second implementation (`Bundle.Finalize(..., suppressReleaseDate)`, `ApplyAmends` with `BundleAmend.PatchesDescription` for the reconciler-owned notes sidecar).
- **Serialization shaping stays out of the domain**: an empty list or a blank title that must not be written is the DTO mapping's job (`ReleaseNotesSerialization`), not an operation's and not a `with` in the writer.
- **The other aggregates have theirs too** (same rules: pure, `Result<T>` through the aggregate's set when one covers it, the plain record when none does).
  - Publishing: `SiteNavigationDefinition.WithoutRepositories(repositories, appended, file)` filters, appends and re-checks with `SiteNavigationConstraints.All` (every finding, positioned in `file`, the value riding along); `SiteNavigationLoader.ForAssembly` decides which repositories and what to append from the assembly configuration and is the loader's only path (`Load` = parse + `ForAssembly`). `Repository.AsConfigurationCheckout()` (a plain record: no set covers a repository alone).
  - Links: `LinkRegistry.WithLinkRegistryEntry(entry)` returns the re-checked registry (errors only, `Derived`; it copies the inner dictionaries, the registry it came from is never modified), `LinkRegistryEntry.FromS3Key(key, eTag, updatedAt, gitReference)`, `LinkManifest.From(origin, urlPathPrefix, pages, crossLinks, redirects)` (the page shaping, ordering and de-duplication a build used to do inline; `Built`) and `LinkManifest.Empty(repository)`. `DocumentationSet.CreateLinkReference()` returns the `Result`; `DocumentationGenerator` logs its findings and writes the value, it does not emit them to the collector (see Findings below).
  - Applies-to: `ApplicableTo.ForStack(...)`, `ApplicableTo.WithoutDiagnostics()`, `AppliesCollection.Of(...)`; plain records, because `ApplicableToConstraints` is not wired (see "Not wired").
  - Git: `GitCheckoutInformation.Resolved/ForElasticRepository/ForClonedRepository/LegacyTestCheckout`; plain records.
  - Search: the one `SearchTuning.None`.
  - Own projects (not in the domain assembly): `SyncPlanLoader.Planned(...)` is how the planner makes a plan (`IDocsSyncPlanStrategy.Plan` returns `Result<SyncPlan>`, checked once, and `IncrementalDeployService` hands it to the validator without checking again); `VersionIndexBuilder.Build` returns `VersionIndexBuild(Index, InvalidKeys, Report)`, the index checked through `VersionIndexLoader.Check` as it is built. Their guard for phase 4 is an assembly-local `internal init`, since the domain's `InternalsVisibleTo` does not reach them.
  - Findings these operations surface and do not report (keep the rule, decide before it reaches the collector): a page without anchors is written without an anchors list and `link-manifest-anchors-present` (error) says every page has one; a manifest built without a resolvable git origin breaks `link-manifest-origin-named`; the planner counts skipped files in `total_sync_requests` and `total-sync-requests-is-add-update-delete` (warning) says it must not.
  - Still built where they are read or checked in place, by design: `AssembledRepository`/`AssembledSite`/`NavigationInAssembly`/`DiscoveredDocset`/`DocsetDiscovery` are check-only views made to be handed straight to a set; `FetchedCrossLinks`, `GenerationResult` and `LegacyPageMapping` are not domain aggregates.

## The compile-time guard: who can create or edit an aggregate

**Production code outside `Elastic.Documentation` and `Elastic.Documentation.Configuration` cannot create or edit an aggregate.** Its setters and constructors are `internal`; reading stays public. `Elastic.Documentation.csproj` grants `InternalsVisibleTo` to `Elastic.Documentation.Configuration` and to every test project, and to nothing else: never add a production assembly to make something compile, give the code a domain operation or a loader instead. Tests build records by hand (`new`, `with`): the rule is "production cannot, tests can". So a record a service holds came from a loader or a checked domain operation.

- **Sealed so far (stage 1, the global configuration):** `AssemblyConfiguration`, `Repository`, `NarrativeRepository`, `PublishEnvironment` (+ `GoogleTagManager`, `Optimizely`); `GlobalCatalog`, `VersioningSystemCatalog`/`VersioningSystem`, `ProductCatalog`/`Product`/`ProductFeatures`, `LegacyUrlMappingCatalog`/`LegacyUrlMapping`; `RelatedLearningCatalog`/`RelatedLearningLink`; `SearchTuning` (+ `QueryRule`, `QueryRuleCriteria`, `QueryRuleActions`, `SynonymGroup`); `CodexConfiguration` (+ `CodexGroupDefinition`, `CodexDocumentationSetReference`); `SiteNavigationDefinition` (+ `SiteSectionRef`, `SiteTableOfContentsRef`, `SiteDropdownLinkRef`, `PhantomRegistration`, `NavigationTocMapping`). `AggregateGuardTests` lists them and fails when one gains a public setter, init accessor or constructor with parameters. Later stages (docset, links, applicability, release notes) follow the same way.
- **Shape.** A property is `{ get; internal init; }`. `required` cannot stay: a required member may not be less visible than its type, so the former `required` members default to `default!` and the loader or operation sets them. A positional record is written out with an internal constructor and a public `Deconstruct`, so `new Type(...)`, an object initializer and `with` fail to compile outside the two assemblies.
- **Serialization.** These aggregates are read from YAML by the loaders and never JSON-deserialized; a type that is deserialized needs the loader assembly or `[JsonInclude]` on its internal setters.
- **A caller that needs a new record** goes through a pure operation in the domain (`CodexDocumentationSetReference.ForRepository`, `Repository.AsConfigurationCheckout`, `SiteNavigationDefinition.WithoutRepositories`), not through an `InternalsVisibleTo` grant.

## Artifact loaders: links, version index, sync plan

Three more artifacts are read from many places (a file, S3, a git clone, the application cache, a CDN), so each has one checked entry and the raw reader is not public.

- **Links** (`Elastic.Documentation.Configuration/Loading/LinkLoader`). `LoadManifest(text|stream, file)` (`links.json`, `LinkManifestConstraints`) and `LoadRegistry(text|stream, file, eTag?)` (`link-index.json`, `LinkRegistryConstraints`) parse, check once and return `Result<T>` with every finding; a text that does not parse (or is `null`) is an error diagnostic and no record. `LinkJson.Deserialize*` is `internal` (the domain's `InternalsVisibleTo` names only `Elastic.Documentation.Configuration`); `LinkJson.Serialize` stays public for writers, also reachable as `LinkLoader.Serialize`. `ILinkIndexReader.GetRegistry/GetRepositoryLinks` return `Task<Result<T>>`, so every reader (S3, git clone) goes through the loader and no consumer can skip the check. The artifact belongs to another repository, so a consumer logs the findings and never fails on them: `result.Unwrap(logger, source)` logs each finding (an error as a warning, a warning as information, anything else as debug; the mapping the `CrossLinkFetcher` always had) and throws only when there is no value. Every `CrossLinkFetcher` path is checked: fetched `links.json`, the link index, and the locally cached `links.json` (an unparsable cache file is logged and refetched, as before). `CodexCloneService`, `RepositorySourcesFetcher` (now reading its snapshot through the filesystem abstraction it already had), `LinkIndexLinkChecker`, `NavigationPrefixChecker`, `RepositoryBuildMatchingService`, `DocSetConfigurationCrossLinkFetcher` and the link-index lambda all read through it.
- **Version index** (`Elastic.Documentation.OpenApiIndex/VersionIndexLoader`). That project does not depend on the domain assembly (the publishing lambda stays small), so its outcome is `VersionIndexLoad(Index, Error, Report)`, not `Result<T>`: `Load(text)` / `LoadAsync(stream)` parse and run `VersionIndexConstraints` once; `Check(index)` is the same gate for an index that was built, which `VersionIndexPublisher` runs before it writes. One definition of a checked version index. `VersionIndexClient` (API explorer, now sharing the entry type and wire format with the publisher) reports the report's errors once per index as global warnings; the index is the CDN's, so a rule it breaks never stops a render.
- **Sync plan** (`Elastic.Documentation.Deploying/Synchronization/SyncPlanLoader`). `Load(json, file)` parses and checks once and returns `Result<SyncPlan>`; `Check(plan)` is the same for the planner's own plan. `SyncPlan.Deserialize` is `internal`. `DocsSyncPlanValidator.Validate(Result<SyncPlan>)` turns the findings into the verdict and does not run the rules again; `Validate(SyncPlan)` checks through `SyncPlanLoader.Check` first. `IncrementalDeployService.Apply` reads the plan through the loader: a plan that does not parse is one error on the plan file (it used to throw), the early return for a plan with no requests is unchanged, and a bad plan is reported once.
- **Not wired, on purpose.**
  - `LinkGraphConstraints`: a `LinkGraph` needs one repository's manifest together with the link registry, the manifests fetched for its targets, the resolved docset and the site navigation. The data exists in the assembler and in a single build but never in one place at one time (the manifest is written at the end of a build, the targets are fetched by the cross-link resolver, the navigation by the assembler), and the resolver already reports M29/M30/M34 with its own messages. Wiring it means a new aggregation step after the build plus de-duplicating those reports; logged as a gap.
  - `ApplicableToConstraints`: `ApplicableTo` is produced by the YAML reader (`ApplicableToYamlConverter`) at three render sites (the directive, the role, the code-block parser), and the reader already reports M94 (versions on versionless keys), M96 (inconsistent versions) and the other conversion problems as diagnostics at those sites. M98 re-reports exactly those diagnostics, so running the set would double every one. The rows that stay with the reader: M94, M96, M92, M98. The rows no reader reports (M87 empty block, M89 nested unknown keys, M91 deprecated lifecycle, M93 non-text values) would be new warnings on every shipped page; they need a decision on severity and a shipped-docs sweep before they run in a build, so they stay test-only (`ApplicableToConstraintsTests`, `ApplicableToAuthoringTests`).
- `LoaderEntryPointTests.NoPublicLoaderMethodReturnsAnUncheckedDomainRecord` covers `LinkLoader`; `LinkLoaderTests` fail when `LinkJson` has a public `Deserialize*` or any domain assembly type exposes a public static `Deserialize*`; `SyncPlanLoaderTests` fail when `SyncPlan.Deserialize` is public; `CrossLinkFetcherCheckTests` fail when an `ILinkIndexReader` method returns a bare record.
