# Constraints conventions: what a loader hides, and how the model shows it

A loader may trim, default, coerce, drop or collapse what a file wrote. The build keeps using the result; the model additionally records what was hidden, so a rule can say "the file wrote X". The loader's behaviour never changes. All of this is AOT-safe: the loader already walks the nodes, no reflection.

| The loader... | The model keeps | Rule reads |
| --- | --- | --- |
| drops keys it does not read | `IReadOnlyList<string> UnknownKeys` on the record built from that mapping, in the order written. Filled with `UnknownYamlKeys.Of(written, known...)` (Configuration/Converters). `[IgnoreEquality]`. | `Each` over the keys, one violation per key, Warning |
| coerces text into a bool or an enum (invalid text falls back to a value) | `<Member>Raw` (`string?`), the text as written; null when the model was not loaded from a file. `[IgnoreEquality]`. | the raw text parses, e.g. `Enum.GetNames<T>().Contains(raw, OrdinalIgnoreCase)` |
| defaults, trims or normalises a value | `Nullean.Entities.Authored<T>` when the member may change type; otherwise the same `<Member>Raw`. | `Raw` against the form the build expects |
| chooses between files | `SourceFileName` (`string?`) on the model | the name |
| collapses duplicate keys of a dictionary | a `DuplicateKeys` list, filled where the dictionary is built (none needed yet) | `Unique` |
| throws on bad input | nothing: the load fails with the loader's message, there is no model. The row stays with the loader. | none |

Rules for the pieces:

- A raw/unknown field never takes part in equality (`[IgnoreEquality]`) and has a default, so code that builds the model by hand needs no change and a hand-built model breaks no rule (null raw is "not authored").
- A rule about something the loader already reports (a diagnostic, an exception) is not added: one report only. Log the row as a gap instead.
- A default that is the dominant idiom of the shipped files (`apm-server:` with no settings, `versioning` omitted because it equals the product id) is not a violation; the field is not added.
- Severity of a new rule on a silent coercion is Warning, unless the catalogue says otherwise.

## Loader pipeline: Parse + Map + Rules

Every loader is three things and nothing else, run through `LoaderPipeline` (Elastic.Documentation.Configuration/Loading):

```csharp
public static Result<SearchTuning> Load(ConfigurationFileProvider provider) =>
    LoaderPipeline.Run(
        "search.yml",
        parse: ReadDto,                       // the only code that touches the DTO (internal)
        map: ToRecord,                        // DTO -> anemic record; findings of its own go in `extra`
        rules: SearchTuningConstraints.All);  // the aggregate's set, from Elastic.Documentation
```

- `Run` catches a step that throws and returns it as an error diagnostic carrying the exception's message, runs `rules.Report` exactly once, and returns `Result<T>` (an error means no value; `errorsAreFatal: false` returns the value with its errors for a caller that reports and continues, a docset or a navigation). `Check` is the same last step for a record built elsewhere; `Build` only builds, for a part whose rules relate it to another part (a pair set the loader runs once both exist).
- The raw parse helpers (`CreateProducts`, `CreateSearchConfiguration`, `AssemblyLoader.Deserialize`, `SiteNavigationLoader.Deserialize`, `CodexSiteLoader.Deserialize`, `ChangelogConfigurationLoader.DeserializeConfiguration`, ...) are `internal`. Outside Configuration there is no way to get a record from text except through the checked loader. Tests see them through `InternalsVisibleTo`.
- A docset has one entry, `DocumentationSetLoader.Load(...)`, which parses, maps and resolves against the catalog (the pair set `DocumentationSetInCatalog`) and returns `Result<LoadedDocumentationSet>`. `LoadMetadata` is the one deliberate unchecked entry (codex reads the registry of repositories it does not build); it returns a `Result` too and is pinned by a test.
- `LoaderEntryPointTests.NoPublicLoaderMethodReturnsAnUncheckedDomainRecord` fails when a public method of a `*Loader` type returns a domain record instead of `Result<T>`, unless it reports to a collector it is given.

## Loader recipe: build, check once, hand the result on

A loader is the one place that checks the entity it builds; nothing downstream checks it again.

1. Build the entity. When a rule relates two things, the loader builds the pair record itself, e.g. `new DocumentationSetInCatalog(docset, products)`.
2. `var report = Set.All.Report(entity);` runs every rule once and reports all of them, not the first.
3. Hand the report on: `Result.From(report, file)` (carries every diagnostic; `HasErrors` is true when a rule of Error severity was broken) or, where the loader owns a collector, `collector.Write(report, file)`, which returns whether the entity is usable. Both go through `ConstraintReport<T>.ToDiagnostics`, the only violation-to-diagnostic mapping, so every diagnostic carries the rule's id as `Diagnostic.RuleId`. Match on that, never on message text.
4. Drop items only through the report, by the typed rule handle: `report.Keep(items, Set.SomeRule)` or `report.Rejected(Set.SomeRule)`, never by comparing a `ConstraintId` string. Only an Error rejects an item; a Warning never drops one.
5. Never check in a callee. A caller of a loader uses `result.EmitTo(collector)` and `result.HasErrors`; it does not run the set again. The `Check(...)` one-liners on the sets are gone: use `Set.All.Report(...)`.
6. Startup-critical configuration stops the process in one place, the composition root: `Loader.Load(...).OrThrow()` throws a `ConfigurationException` whose message lists every error and which carries every diagnostic.

## Ownership: three owners, by lifetime

Services never load. Whoever owns a loader is decided by how long what it loads lives.

1. **Global configuration (the process).** `GlobalConfigurationLoader.LoadOnce(provider)` is the only entry: `assembler.yml`, `versions.yml`, `products.yml`, `legacy-url-mappings.yml` and `search.yml` load once per provider and come back as one `Result<GlobalConfiguration>` carrying every diagnostic, so `OrThrow()` at the composition root (`AddDocumentationServiceDefaults`) lists every error of every file. Its non-error diagnostics are registered as the singleton `StartupDiagnostics`. The owner of a collector drains it exactly once per process: `DocumentationTooling` does it when it creates the console collector, so every command family (build, codex, changelog, assembler...) reports a catalogue warning once. A host with no collector (API, MCP server) calls `StartupDiagnostics.LogTo(logger)`; a lambda that loads one file itself (`AssemblyLoader.LoadYaml`) decides for itself and ignores warnings. `related-learning.yml` is not global: it loads on first use (`IConfigurationContext.RelatedLearning`), because only documentation builds need it.
2. **Context-scoped (a build, an assemble run, a codex).** The context owns its loader and loads once (docset: `BuildContext`; navigation: `AssembleContext`), and the context is created once per run, never per service. `AssembleContextProvider` (a DI singleton) hands every assembler service and command the same `AssembleContext` for an environment/collector/directory combination, so the navigation is parsed, checked and its diagnostics emitted once per run; a service asks `contexts.Get(environment, collector, fileSystem)` instead of `new AssembleContext(...)` (tests may still construct one directly). A docset is per repository by nature: one `BuildContext` per docset is the intended lifetime. What a directive needs from the run comes from the build context, not from a loader of its own: `BuildContext.PrivateRepositoryNames` (the assembly configuration loaded at startup) and `BuildContext.BundleLoader` replace `AssemblyLoader.LoadOnce` and `new BundleLoader` inside `{changelog}`. A directive's own YAML/JSON body with no domain record and no constraint set (`{settings}` tables, `{whatsnew}` central config, the Storybook registry, csv includes) is a directive-local format: it stays with the directive.
3. **Artifact loaders (a command or a call).** Changelog configuration, entries, bundles, link manifests, the sync plan. `ChangelogConfigurationLoader` returns `Result<ChangelogConfiguration>` (`Load`, `LoadRequired`, `LoadForProfileMode`); the command owns one and hands it to the services it creates (`configurationLoader:`), a service created without one (tests, CI commands over a runner temp file system) makes its own. It is deliberately not cached: a command reads `changelog.yml` once or twice, and a cache keyed by path would serve a stale file to anything that rewrites it (every test does).

**Plain transport, on purpose.** Three reads stay in their service because there is no domain record with a constraint set to check them against, so a loader would only rename `JsonSerializer.Deserialize`: the redirects mapping `DeployUpdateRedirectsService` pushes to the key-value store (`Dictionary<string, string>`; a missing or unparsable file is already an error diagnostic on the file), the build's `GenerationState` (`DocumentationGenerator.GetPreviousGenerationState`, a private cache of the previous build that is only a hint for incremental builds), and the Storybook registry (a directive-local format, see above). The moment one of them gains a constraint set it moves into a loader next to the others. The link-index snapshot `CodexCloneService` reads is not one of them: it goes through `LinkLoader.LoadRegistry`.

`LoaderEntryPointTests.NoPublicLoaderMethodReturnsAnUncheckedDomainRecord` has no exemption left: a public loader method returns `Result<T>`, even where the parser reports to a collector internally (the changelog loader buffers that into the result).

A rule is not wired into a loader when something already reports the same problem with a different message or severity, or when the rule is stage dependent (its description says so): wiring it would report twice or report at the wrong stage. Log the row as a gap instead.

## Artifact loaders: release notes

Changelog entries and bundles are artifacts read from many places (a folder, CDN content, S3, git), so their loader is not one `Load` but a small set of entry points in `Elastic.Documentation.Configuration/ReleaseNotes`, and **nothing else touches the file's shape**: the DTOs (`ChangelogEntryDto`, `ProductInfoDto`, `Bundle*Dto`, `*MinimalDto`) and `ReleaseNotesSerialization` are `internal` (tests see them through `InternalsVisibleTo`).

- `ReleaseNotesLoader.LoadEntry(text, fileName, file?)` and `LoadBundle(text, file)` parse, map and check once, returning `Result<T>`. A file that does not parse (or is empty) is an error diagnostic and no record; a file that parses always returns its record with every finding, so the caller, which knows whether a rule error stops it, decides. `Serialize(entry|bundle)`, `NormalizeYaml` and `ToEntry(BundledEntry)` are the writer side: a writer never needs a DTO.
- `BundleLoader.LoadBundles(folder)` and `LoadBundlesFromContent(...)` (CDN) return `Result<IReadOnlyList<LoadedBundle>>`. The findings are always in the result (no optional callback): an unparseable bundle or an entry without inline content is an error diagnostic (the bundle or entry is skipped), a broken rule is reported at its own severity, then `LoadedBundleConstraints` runs once on what was loaded. The directive forwards each diagnostic; the CDN fetcher forwards each as a warning (an inferred product must not fail the build).
- **Stage-dependent rules are separate sets, not flags.** A rule whose description says "stage dependent" does not run at read time. The read-stage sets are `ChangelogEntryReadConstraints.All` (marker integrity only), `BundleReadConstraints.All` (not `bundle-entries-inlined`, which the loader enforces with its own pinned warning, nor `bundle-entry-files-unique`, a render CLI rule) and `LoadedBundleReadConstraints.FromContent` (no file-name convention for CDN objects). Each is written as `Full.All.Without(Full.RuleA, Full.RuleB)` with typed handles (`ConstraintSet<T>.Without(params Constraint<T>[])`), so the suppression is visible, survives a rename, and a rule removed from the full set breaks the build.
- The authoring stage reads the file's own shape, which a record cannot carry (an unrecognized type, `versions` on an entry, the raw lifecycle text), so `ChangelogEntryValidator` (`validate-entries`) lives beside the loader and takes the file's text, not a DTO. Its messages are pinned by tests and differ from the constraint set's, so it stays the validate stage's own report; `BundleBuilder` likewise keeps its `missing required field` messages.
- `LoaderEntryPointTests.ReleaseNotesDtosAreInternal_AndTheirLoadersReturnCheckedResults` fails when a release-notes DTO or the raw serializer is public, or when `ReleaseNotesLoader`/`BundleLoader` hand out a record (or a collection of records) outside a `Result<T>`.

## Domain operations: derive, then re-check

A record that is not read from a file (built from a pull request, assembled from files, scrubbed, merged, amended) is made by a **domain operation**, never by `new` or `with` in a service. The release-notes records have them in `Elastic.Documentation/ReleaseNotes` (`ChangelogEntry.FromPullRequest/Create/Marker/SourcePointer/CanonicalKeyAndMarkers`, `ProductReference.Parse`, `Bundle.Assemble/ForRelease/Finalize/AmendOf/ApplyAmends/WithoutPrivateLinks`, `BundledEntry.Inline/Exclusion/AppendContinuation/ToNote`, `entry.ToBundledEntry(file, checksum)`, `LoadedBundle.MergeByTarget`, `LinkAllowlist`).

- **Pure.** No IO, no clock (the caller passes `today`), no collector. A finding is a diagnostic in the result, in the order it was found, so a service forwards them with the same messages as before (`result.EmitTo(collector)`).
- **Returns `Result<T>`** (`Elastic.Documentation.Diagnostics`), the record checked by the aggregate's set. The set is the stage's: the read-stage sets (`ChangelogEntryReadConstraints`, `BundleReadConstraints`, `LoadedBundleReadConstraints`) unless the rule the operation must hold is stage dependent, in which case the set is written `Full.All.Without(handles)` like they are; a pinned message is never weakened to make an operation pass.
- **Built, then derived.** `DomainOperation.Built` is for a record made from facts that were never in a file: the result carries every finding of the set. `Derived` is for a record made from one that was already checked: the set runs again (a derivation can break a rule its source kept, so the result is re-checked), but only the errors are in the result, because the warnings the source carried were reported when it was read. A caller of `Derived` writes `result.EmitErrorsTo(collector)`.
- **The value rides along.** `Result.From` keeps the value even when a rule of Error severity is broken, so a caller that tolerates the finding can still use it; `EmitErrorsTo` returns null instead.
- **A part with no set of its own** (`ProductReference`, `BundledEntry`) is not wrapped in a `Result` that checks nothing: its operations return the part, and the entry or bundle that holds it is what is checked.
- **Where two copies differed, the difference is a parameter**, not a second implementation (`Bundle.Finalize(..., suppressReleaseDate)`, `ApplyAmends` with `BundleAmend.PatchesDescription` for the reconciler-owned notes sidecar).
- **Serialization shaping stays out of the domain**: an empty list or a blank title that must not be written is the DTO mapping's job (`ReleaseNotesSerialization`), not an operation's and not a `with` in the writer.
- **The other aggregates have theirs too** (same rules: pure, `Result<T>` through the aggregate's set when one covers it, the plain record when none does).
  - Publishing: `SiteNavigationDefinition.WithoutRepositories(repositories, appended, file)` filters, appends and re-checks with `SiteNavigationConstraints.All` (every finding, positioned in `file`, the value riding along); `SiteNavigationLoader.ForAssembly` decides which repositories and what to append from the assembly configuration and is the loader's only path (`Load` = parse + `ForAssembly`). `Repository.AsConfigurationCheckout()` (a plain record: no set covers a repository alone).
  - Links: `LinkRegistry.WithLinkRegistryEntry(entry)` returns the re-checked registry (errors only, `Derived`; it copies the inner dictionaries, the registry it came from is never modified), `LinkRegistryEntry.FromS3Key(key, eTag, updatedAt, gitReference)`, `LinkManifest.From(origin, urlPathPrefix, pages, crossLinks, redirects)` (the page shaping, ordering and de-duplication a build used to do inline; `Built`) and `LinkManifest.Empty(repository)`. `DocumentationSet.CreateLinkReference()` returns the `Result`; `DocumentationGenerator` logs its findings and writes the value, it does not emit them to the collector (see Findings below).
  - Applies-to: `ApplicableTo.ForStack(...)`, `ApplicableTo.WithoutDiagnostics()`, `AppliesCollection.Of(...)`; plain records; the set runs where a block is read from a file (see "Where the last five sets are wired").
  - Git: `GitCheckoutInformation.Resolved/ForElasticRepository/ForClonedRepository/LegacyTestCheckout`; plain records.
  - Search: the one `SearchTuning.None`.
  - Own projects (not in the domain assembly): `SyncPlanLoader.Planned(...)` is how the planner makes a plan (`IDocsSyncPlanStrategy.Plan` returns `Result<SyncPlan>`, checked once, and `IncrementalDeployService` hands it to the validator without checking again); `VersionIndexBuilder.Build` returns `VersionIndexBuild(Index, InvalidKeys, Report)`, the index checked through `VersionIndexLoader.Check` as it is built. Their guard for phase 4 is an assembly-local `internal init`, since the domain's `InternalsVisibleTo` does not reach them.
  - Findings these operations surface and do not report (keep the rule, decide before it reaches the collector): a manifest built without a resolvable git origin breaks `link-manifest-origin-named`; the planner counts skipped files in `total_sync_requests` and `total-sync-requests-is-add-update-delete` (warning) says it must not.
  - Still built where they are read or checked in place, by design: `AssembledRepository`/`AssembledSite`/`NavigationInAssembly`/`DiscoveredDocset`/`DocsetDiscovery` are check-only views made to be handed straight to a set; `FetchedCrossLinks`, `GenerationResult` and `LegacyPageMapping` are not domain aggregates.

## The compile-time guard: who can create or edit an aggregate

- **Required members are public `init`.** They carry the `required` keyword, so `new X { ... }` must set every one; CS9032 means a required member cannot be less visible than its type, so they cannot be internal. System.Text.Json honours the keyword, so a missing key is still a parse error.
- **Optional members are `{ get; internal init; }`** and a positional record has an internal constructor and a public `Deconstruct`: only `Elastic.Documentation`, `Elastic.Documentation.Configuration` and the test projects (`InternalsVisibleTo`; never add a production assembly) can set them or call the constructor. `SyncPlan` and `VersionIndexEntry` do the same with an assembly-local grant for their own test project.
- **Loaders and domain operations are the intended path** (`CodexDocumentationSetReference.ForRepository`, `Repository.AsConfigurationCheckout`, `SyncPlanLoader.Planned`); a record a service holds should have come from one of them. Each type's `<remarks>` says which.
- **Accepted gap:** an outsider can still build a record with only its required members. To be solved later.
- **Serialization.** The JSON-read types carry `[JsonInclude]` on their internal members; a source-generated serializer in another assembly cannot reach an internal setter, so `CreateRules` keeps its `CreateRulesJsonConverter`. `SerializedAggregateTests` read a sample of each and check every field.
- **Guard tests** (`AggregateGuardTests` stages 1 and 2, `SyncPlanGuardTests`, `VersionIndexEntryGuardTests`) fail when a member without `required` gains a public setter or init, or a sealed type gains a public constructor with parameters.
- **Left public on purpose (not aggregates):** check-only views made to be handed straight to a set (`AssembledRepository`, `AssembledSite`, `NavigationInAssembly`, `DiscoveredDocset`/`DocsetDiscovery`, `LinkGraph`, `DocumentationSetInCatalog`, `ChangelogConfigurationInCatalog`, `ChangelogEntryInConfiguration`, `BundleAmendOfParent`, `LoadedBundles`); inputs of a pure operation (`LinkPage`, `PullRequestFacts`, `CreateEntryFacts`, `CanonicalPlacement`, `BundleSource`, `BundleProductSpec`, `BundleAmend`, `PrivateLinkScrub<T>`, `ResolveResultWithRule`); the rejection/evidence records of constraint sets (`RejectedApi`, `RejectedApiChild`, `DeclaredBrandingImage`); transport and runtime state (`GenerationState`, `FetchedCrossLinks`, `GenerationResult`, `LegacyPageMapping`, `SyncRequest` and its `Add`/`Update`/`Delete`/`Skip` subtypes, which only the planner in the same assembly fills); value types (`SourceLocation`, `DocsetPath`/`ContainerPath`/`DeclaringFilePath`, `VersionOrDate`, `SemVersion`/`VersionSpec`, `ProductLifecycle`).

## Artifact loaders: links, version index, sync plan

Three more artifacts are read from many places (a file, S3, a git clone, the application cache, a CDN), so each has one checked entry and the raw reader is not public.

- **Links** (`Elastic.Documentation.Configuration/Loading/LinkLoader`). `LoadManifest(text|stream, file)` (`links.json`, `LinkManifestConstraints`) and `LoadRegistry(text|stream, file, eTag?)` (`link-index.json`, `LinkRegistryConstraints`) parse, check once and return `Result<T>` with every finding; a text that does not parse (or is `null`) is an error diagnostic and no record. `LinkJson.Deserialize*` is `internal` (the domain's `InternalsVisibleTo` names only `Elastic.Documentation.Configuration`); `LinkJson.Serialize` stays public for writers, also reachable as `LinkLoader.Serialize`. `ILinkIndexReader.GetRegistry/GetRepositoryLinks` return `Task<Result<T>>`, so every reader (S3, git clone) goes through the loader and no consumer can skip the check. The artifact belongs to another repository, so a consumer logs the findings and never fails on them: `result.Unwrap(logger, source)` logs each finding (an error as a warning, a warning as information, anything else as debug; the mapping the `CrossLinkFetcher` always had) and throws only when there is no value. Every `CrossLinkFetcher` path is checked: fetched `links.json`, the link index, and the locally cached `links.json` (an unparsable cache file is logged and refetched, as before). `CodexCloneService`, `RepositorySourcesFetcher` (now reading its snapshot through the filesystem abstraction it already had), `LinkIndexLinkChecker`, `NavigationPrefixChecker`, `RepositoryBuildMatchingService`, `DocSetConfigurationCrossLinkFetcher` and the link-index lambda all read through it.
- **Version index** (`Elastic.Documentation.OpenApiIndex/VersionIndexLoader`). That project does not depend on the domain assembly (the publishing lambda stays small), so its outcome is `VersionIndexLoad(Index, Error, Report)`, not `Result<T>`: `Load(text)` / `LoadAsync(stream)` parse and run `VersionIndexConstraints` once; `Check(index)` is the same gate for an index that was built, which `VersionIndexPublisher` runs before it writes. One definition of a checked version index. `VersionIndexClient` (API explorer, now sharing the entry type and wire format with the publisher) reports the report's errors once per index as global warnings; the index is the CDN's, so a rule it breaks never stops a render.
- **Sync plan** (`Elastic.Documentation.Deploying/Synchronization/SyncPlanLoader`). `Load(json, file)` parses and checks once and returns `Result<SyncPlan>`; `Check(plan)` is the same for the planner's own plan. `SyncPlan.Deserialize` is `internal`. `DocsSyncPlanValidator.Validate(Result<SyncPlan>)` turns the findings into the verdict and does not run the rules again; `Validate(SyncPlan)` checks through `SyncPlanLoader.Check` first. `IncrementalDeployService.Apply` reads the plan through the loader: a plan that does not parse is one error on the plan file (it used to throw), the early return for a plan with no requests is unchanged, and a bad plan is reported once.
- **Where the last five sets are wired.** Each rule has one emitter; where a legacy emitter says the same thing in wording a test pins, it stays and carries the rule's id, and the set run at that point leaves the rule out (a `Full.All.Without(...)` set, like the read-stage sets of the release notes), so a problem is never said twice.
  - `ApplicableToConstraints` (`ApplicableToReadConstraints.All`, run once on every `applies_to` block read from a file: the directive, the role, the code block, an `{applies-item}`, an admonition's `:applies_to:` and a page's front matter; `ProcessorDiagnosticExtensions.ReportApplicableTo`, `MarkdownFile.ProcessYamlFrontMatter`). The reader (`ApplicableToYamlConverter`) still collects its findings on `ApplicableTo.Diagnostics`; M98 reports them at their own severity, and a finding made for a problem another rule covers carries that rule's id (`ApplicabilityDiagnostic.RuleId`): M94 (versions on versionless keys, worded with the key as written: `ech`, `serverless`) and M96 (version consistency). The read set leaves M94 and M96 out for that reason. M91 (deprecated lifecycle) is the rule's alone now (the reader's hint is gone; the rule names the lifecycle as written, once per lifecycle with every key that uses it); M92, M89, M93 and M87 are new emitters (M87 does not fire for a block the reader already reported on). Findings carry no line for front matter, the line of the directive/role elsewhere. A block read from a toc entry or the docset (`FallbackAppliesTo`) is not checked: its diagnostics have no position to report at.
  - `ChangelogEntryInConfigurationConstraints` (`validate-entries`: `ChangelogEntryValidator.Check(..., products)`, `ChangelogEntryValidateConstraints.InConfiguration`). The validator reads the file's text and reports product, subtype, lifecycle and area membership (and the rules of `ChangelogEntryConstraints` it overlaps) with its pinned wording, now with `EntryFileFinding.RuleId`; the service writes each finding with that id. The rules the text cannot answer run on the entry the file reads as: a recognized type the configuration does not list (R37) and a product outside `products.available` (R6).
  - `LoadedBundlesConstraints` (render CLI: `BundleValidationService` builds `LoadedBundles` from the validated inputs with `LoadedBundle.Of` and reports once). R89's message is the rule's now (the service's own warning is gone); R88 is a Hint, because rendering several bundles of one target is how a merged release is written. The directive and the CDN path do not run it: they merge same-target bundles by design.
  - `BundleAmendConstraints` (`ChangelogBundleAmendService.AmendHoldsToRules`): the amend about to be written is checked against the effective bundle (parent plus existing amends) before the write. R92 (removal not in the bundle, checksum mismatch) and R93 (addition already in the bundle) are the only emitters; the service's own two errors are gone and their wording moved into the rules. With `--force` the checksum mismatch is a warning and the exclusion is written with the bundle's checksum as before; every other error stops the write.
  - `LinkGraphConstraints` (`LinkGraphIsolatedConstraints`, run by `DocumentationGenerator` after a full isolated build, from the manifest it just made, the registry and manifests `DocSetConfigurationCrossLinkFetcher` kept on `FetchedCrossLinks`, and the resolved docset). M30, M31 and M34 are the cross-link resolver's, reported at the link with the rules' ids (`ICrossLinkResolver.TryResolve(Action<string, string?>, ...)`; directive links are tagged too); the graph run leaves them out, and N15 (no site navigation in one repository). It runs M29, N24, N29, N20 and N47. Not wired: the assembler's graph (every repository's manifest, its own registry and the site navigation exist together only in the assembler build, which has no `FetchedCrossLinks.Registry`), and a build against a codex registry as well as the public one.
- `LoaderEntryPointTests.NoPublicLoaderMethodReturnsAnUncheckedDomainRecord` covers `LinkLoader`; `LinkLoaderTests` fail when `LinkJson` has a public `Deserialize*` or any domain assembly type exposes a public static `Deserialize*`; `SyncPlanLoaderTests` fail when `SyncPlan.Deserialize` is public; `CrossLinkFetcherCheckTests` fail when an `ILinkIndexReader` method returns a bare record.

## Testing: `Laws` over generated data

Every constraint set has a `Laws` test, and 26 of the 28 run it over **generated** records instead of one hand-written value: `Set.All.Laws(gen, CounterExamples)` (`Nullean.Entities.CsCheck`, `Gen<T>` overload). The laws are the same four, now over generated data: 300 records from a fixed seed (so a failure replays) break no rule (a failure prints the record and the rules it broke); every rule has a name and a counter-example; every counter-example, applied to the first 25 generated records, breaks its rule for at least one of them (the rule is reachable) and breaks **only** its rule for each. About 0.7 s for all 26.

- **The generator is `DomainGen.Of<T>(configure)`** (`tests/Elastic.Documentation.Tests/Domain/DomainGen.cs`): `GenAuto` in `Plausible` mode with the shared leaf generators (`SemVersion`) and the catalog invariants, plus the aggregate's own declarations. It reaches `internal init` setters and internal constructors by reflection (the aggregates are sealed that way, see above), so a test builds nothing by hand to get a valid record.
- **Declare what a loaded record promises, once.** `Reference<TFrom, TTo, TKey>` for a member that names another record's key (`DocumentationSetDefinition.CodexGroup` names a `CodexGroupDefinition.Id`), `Identity` for a key unique across the value (changelog files, query rule ids, codex group ids), and `Normalize<T>` for a derived or coupled member a generator cannot guess (a bundle's `ReleaseDateRaw` is its `ReleaseDate` written out; an assembler's available, private and all-private repositories derive from its references; a registry's paths derive from its keys; a navigation's mounts get one repository, source and prefix each). A normalizer is the model's invariant written next to its test; the constraint set then checks it independently, so a normalizer that forgets a promise shows up as a generated record that breaks a rule, not as a silently narrower generator.
- **A counter-example is `Func<T, T>` written against the generated record**: it adds or replaces the one piece that is wrong, under a name the generator never uses (`dup-a`, `unpublished`, `beats`), so it holds whatever was generated. It does not assume a repository, page or product exists in the base.
- **A set stays hand-written (`Laws(Valid(), ...)`) when no honest generator exists, and says why in a comment above the test.** `DocumentationSetInCatalog` (a toc and a file system that must agree, 25 of its 70 rules) and `ChangelogConfigurationInCatalog` (a web of ids across Pivot, Bundle, Rules and the product catalog, 18 of 31 rules): drawn members break many rules at once, and a normalizer for them is the loader's resolution logic written again. The way to cover them is a model-first `Gen` (a set of page paths, then the files and the toc built from it; a product subset, then the configuration built around it), not a repair of drawn members.
- **Generated records are valid, so each rule's breaking value is its counter-example.** A rule no counter-example can break alone fails the test (`requireCounterExamples`), as before.

### Operation laws and loader laws

`Laws` says a record is valid; the property tests say what the code that makes, changes and reads records preserves. They are plain CsCheck properties over the same generators (`DomainGen`, `BundleExamples`, `ChangelogEntryExamples`, `LinkExamples`), with a **fixed seed** (`Props.Check`: `Props.Seed`, 200 iterations, one thread, so a run is the same run and a failure prints a shrunk input). Each test carries a doc comment with the law and the consequence if it is broken, because a generated input is invisible and the comment is the only place a reader learns what is guaranteed. `Props.cs` is linked into every test project that has such laws; the generators of the domain tests are linked into the Configuration tests the same way.

- **Operation laws** (`tests/Elastic.Documentation.Tests/Domain/ReleaseNotesOperationProperties.cs`, `OperationProperties.cs`; `Elastic.Documentation.Deploying.Tests/SyncPlanProperties.cs`; `Elastic.Documentation.OpenApiIndex.Tests/VersionIndexProperties.cs`). An operation over any generated input returns its `Result<T>` and never throws, and its verdict is the read-stage set's own (`result.HasErrors` equals the errors of `XReadConstraints.All` on the value; no operation has a private idea of valid). Then the algebra of each: `WithoutPrivateLinks` is idempotent and leaves nothing `LinkAllowlist.ValidateNoPrivateReferences` would refuse (entry, bundled entry, bundle); `Marker(n)` satisfies the full entry rules; `CanonicalKeyAndMarkers` names the lowest PR and every marker points at it; `ToBundledEntry` then `ToNote` keeps type, title, areas, PRs and issues; `Finalize` is deterministic for a `today` and follows the release-date rule; `WithLinkRegistryEntry` is monotonic, idempotent, keeps the newer entry and leaves its input alone; `FromS3Key` is an entry or an `ArgumentException`; `WithoutRepositories` removes the mounts and phantoms of the removed repositories (children promoted out of a removed mount are kept, as documented) and re-checks; `MergeByTarget` keeps every entry, has one bundle per version, newest first; `SyncPlanLoader.Planned` keeps every request and states their sum; `VersionIndexBuilder.Build` keeps the highest minor of each major whatever order the keys arrive in. A law that fails is a finding: the test stays strict and is skipped with a `FINDING 5b:` reason naming the minimal reproduction (`ApplyAmends` is not idempotent for amends that add entries; `MergeByTarget` is not order independent because the first bundle's metadata wins), with the weaker law that does hold beside it.
- **Loader laws** (`tests/Elastic.Documentation.Configuration.Tests/LoaderProperties.cs`, plus the plan and index laws above). The corpus is the shipped baseline text; the variants are the same text with a line dropped, swapped or repeated, truncated, a key added, a tab or a junk line put in, a value replaced by a list or `~` (`Mutations`). (1) **Load twice**: the same text gives equal records and the same diagnostics, for assembler, catalogs, search, related learning, navigation, codex, docset and changelog configuration. (2) **Round trip**: a generated valid entry, bundle, links.json, link-index.json and sync plan written by the writer and loaded again is the record that was written, compared as the file says it (an empty list is written as no list, the PR number is the file name's, the obsolete `target` is never written; `AsWritten` in the test is that rule). (3) **Total**: no text makes a loader throw anything but what it documents; the whitelist is per entry point (`SiteNavigationLoader.Load` lets a YAML parser exception out, as its summary says; every other entry point returns a `Result`), so a new exception type is a failing test, not a silent change.
- **The YAML loader laws run in parallel**, and a failure under parallel load is first read as a text, not a race: the `NullReferenceException` and the 100% CPU spin they once showed were a non-mapping entry in `navigation.yml` that a converter loop never consumed and values left empty (`LoaderTerminationTests` holds them), and they fail alone on one thread.

### Service algorithm laws

The pure logic of a service is a property too, next to the project it belongs to, with the same `Props.Check` (fixed seed, 200 iterations) and the same doc comment per law. Logic trapped inside an I/O class is made a pure static function first, and the service calls it (`SyncPlanner.Compute`, which `AwsS3SyncPlanStrategy` feeds with the listings, the ETags and a file-exists function).

- **Sync plan** (`Elastic.Documentation.Deploying.Tests/SyncPlannerProperties.cs`): add, update, skip and delete partition the union of local and remote files (an excluded path is in no list, a local symlink counts as a local file); applying a plan to the remote listing and planning again gives no add, update or delete; a delete is only a remote key with no local file that no exclude matches; the plan does not depend on the listing order; the delete threshold is never below the user's, 0 for an empty bucket, at least 0.8 up to 100 remote files and 0.5 up to 1,000, and the validator's verdict is exactly "listing complete, source files present, delete ratio within the threshold".
- **Navigation** (`Navigation.Tests/Assembler/NavigationResolutionProperties.cs`): a cross-link resolves to the longest mount whose source is the link's path or a whole-segment prefix of it (`reference/apm` does not claim `reference/apm-agents/x`); resolution and the sub-paths the prefix checker compares do not depend on mount order; sub-paths are folders under the mount prefix and prefix-closed; the declared path prefixes and every mount rule are stable when the mounts are reversed or moved into a section; a repeated prefix is always reported (same repository: `RepositoryPathPrefixesUnique`, two repositories: `PathPrefixesUnique`); N14 fires exactly on a source that is a text-only prefix of another.
- **Cross-link redirects** (`Elastic.Markdown.Tests/CrossLinks/CrossLinkResolutionProperties.cs`): for any redirect graph (chains, cycles, self redirects, 'many' rules, targets in other repositories, anchors) resolving a link terminates, never throws, gives a URL and no error or no URL and an error, and gives the same answer twice. A redirect is one hop: the resolver never follows a redirect onwards, so a chain resolves to the page named by the first `to` and a cycle cannot loop; `RedirectNoChains` (N30) is the rule that tells the author a chain exists, and it reports every local chain or cycle (but see the finding below).
- **Versions** (`Elastic.Documentation.Tests/Domain/VersionProperties.cs`): a `SemVersion` printed and parsed is the version; its order is total (reflexive, antisymmetric, transitive) and consistent with equality and the hash code; a prerelease precedes its release; `VersionOrDate` orders mixed semver, date and free text totally; a `VersionSpec` printed and parsed is the spec (kind, bounds, shown patch), the printed form of a parse is a fixed point, and the order of specs is a total preorder; `BaseNotAfterCurrent` fires exactly when base is after current.
- **Changelog matching** (`Elastic.Changelog.Tests/Bundling/ChangelogMatchingProperties.cs`): product filters are alternatives, so adding one only adds entries, and a filter that names a target or a lifecycle never matches more than the same filter with a wildcard (the filters are not a conjunction: narrowing is by pattern, not by adding a filter); product, target and lifecycle patterns are case-insensitive; content is deduplicated by checksum (first file wins, comments do not change the checksum, feeding the files twice is feeding them once, the checksums do not depend on the order); a PR filter only keeps entries naming a requested PR and only grows with it; `BuildBundle` keeps every matched entry once; a product spec list printed and parsed is the list.
- **Findings of these laws, kept strict and skipped with `FINDING 5c:`**: a bundle product filter is compared as written, while the create side normalises `_` to `-` inline in seven places (`ProductFilter_UnderscoreSpelling_MatchesTheHyphenatedProduct`); `RedirectNoChains` takes its sources from the local redirects only, so a local redirect onto a page that redirects to another repository is not reported (`ChainsThroughACrossRepositoryRedirect_AreReportedByNoChains`).
- **Bugs these laws found and fixed**: `PublishEnvironmentUriResolver` compared a cross-link with a mount source by a plain `StartsWith`, so `elasticsearch://reference` resolved through a mount of `elasticsearch://ref/` to `…/erence` (now a whole-segment match); `SemVersion.CompareTo` compared a prerelease with the other version's build metadata, so a prerelease version was less than itself, `1.0.0` compared greater than `1.0.0+m` and the reverse as equal (now ties break on the metadata, so the order is consistent with equality).

## Loaders are thread-safe

The assembler loads many documentation sets at once, so a loader (and the converters in the deserializer it uses) is a pure function of its input and holds no state of its own.

- The shared `ConfigurationFileProvider.Deserializer` and every `IYamlTypeConverter` registered on it are **stateless**: a converter builds its lists and dictionaries in `ReadYaml` and returns them; it never keeps a field it writes, and nothing diagnostic is gathered in a static or instance collection. What a converter must hand back beyond the value goes through the value (`UnknownKeys`, a `HintTypeSet`) or, where a converter has no other way out, `TocAuthoringSink`: `[ThreadStatic]`, opened and closed inside one synchronous load (never across an `await`).
- Static fields hold constants, frozen collections, compiled patterns or a `ConditionalWeakTable` / `ConcurrentDictionary` cache keyed by what it caches. A static `List`, `Dictionary` or `HashSet` that any code path mutates is a bug; a shared `None` or `Empty` record holds only read-only collections.
- A converter loop consumes an event on every path (`SkipThisAndNestedEvents` for what it does not read); a loop that can leave one unread spins forever on a stray line.
- Proof: `ConcurrentLoadTests` runs every entry point over the shipped text and its bent variants on 32 threads and compares each outcome with the one it gives alone, with a timeout so a regression fails instead of hanging.

## Double reporting: one emitter per problem

A problem is reported by one emitter. While a legacy emitter (a hand-written `EmitError` in a loader or a parser) and a constraint report both describe the same problem, the legacy emitter tags its diagnostic with the **same `RuleId`** as the rule, at the same file, line, column, severity and message, so the output shows it once.

- Two ways to make the rule the only emitter: delete the legacy emission (the rule's wording becomes the output; do this when no test pins the old wording, or move the wording into the rule), or keep the legacy emission because it knows what the model does not (the key as written, the position of a link, the file's raw text) and leave the rule out of the set that runs there (`ApplicableToReadConstraints`, `ChangelogEntryValidateConstraints`, `LinkGraphIsolatedConstraints`). Either way the diagnostic carries the rule's id.
- `DiagnosticsCollector.Write` drops an exact duplicate (same non-empty `RuleId`, file, line, column, severity and message as one already written in the run). A dropped duplicate is not counted in `Errors`/`Warnings`/`Hints` and not output. A diagnostic without a `RuleId` is never deduplicated, so untagged legacy emitters behave as before.
- The dedupe hides a double emission from the output, so the dropped duplicates are kept in `DiagnosticsCollector.DuplicatesDropped`. It is the guard: the Authoring generator (`AuthoringGenerator.GenerateAsync`) and the Configuration `CapturingDiagnosticsCollector` (every golden and shipped-configuration load) fail when it is not empty. A failure means two emitters report one problem: remove the legacy emitter once the rule covers it; do not widen the dedupe.
- A collector that overrides `Write` calls `Accept(diagnostic)` (it returns `false` for a dropped duplicate) instead of `IncrementSeverityCount`, so the counts and the output agree.

## Amend order and product spelling

- **Amends are numbered, so their order is defined by the domain, not the caller.** `Bundle.ApplyAmends` applies amends by `BundleAmendMerger.GetAmendMergeOrder(FilePath)` (`.amend-1`, `.amend-2`, ..., the `.amend-notes` sidecar last), ties by file path (ordinal); an amend without a path keeps the order it was given in, after the ones with a path. It is idempotent: an added entry whose file name and checksum are already in the bundle is not added again, so applying the same amends twice is applying them once. `LoadedBundle.MergeByTarget` takes the bundles of one version in a canonical order (release date ascending, undated last, then file path, repository, owner; ordinal) and its result does not depend on the order the file system listed them in.
- **One product spelling function: `ProductNames.Normalize`** (trim, `_` to `-`, case kept, null is empty). Every place that compares a written product id with a catalog id or with another written one uses it, including the product filter of a bundle (`ChangelogEntryMatcher`, which then compares ignoring case); an inline `Replace('_', '-')` on a product id is a bug.

## Required members are rules

- **A `required` or get-only reference member of a `[Constraints]` companion's type gets a generated rule `<member>-required`** (kebab id, `Violation.Member` set), reported with the others. The implicit rule is null-only: an empty string passes. Put `[Required]` on the member for the full DataAnnotations meaning (blank strings fail); that replaces the implicit rule.
- **Opt out with `[Constraints(ImplicitRequired = false)]`, with a comment saying why** (a check-only view, a type an enclosing constructor always fills). Nullable members (`T?`) and value types never get one.
- **The Laws tests prove each rule with a counter-example that nulls the member** (`["repositories-required"] = v => v with { Repositories = null! }`). The other rules read the member unguarded, so the Laws run through `RequiredGate.GatedByRequired()`: a value a `*-required` rule rejects is reported by that rule alone.
- **Gap: only the annotated type's own properties are covered.** Nested record types (`Product`, `QueryRule`, `VersioningSystem`, `LegacyUrlMapping`, `Cta`, ...) get no `*-required` rule unless they have a companion of their own mapped into the parent set.
